## قرار الإصدار

لا يُنشر التطبيق بوصفه جاهزًا للإنتاج قبل إغلاق بوابات الإصدار التالية:

1. لا توجد استجابات أو حصص أو حسابات تجريبية تُعرض على أنها حقيقة.
2. تصدير الليزر والطباعة يطابق ملف المستخدم فعليًا، أو تُعطّل/تُسمّى هذه الأدوات بوضوح إلى أن يكتمل تنفيذها.
3. مفاتيح API لا تُحفظ مكشوفة في `localStorage`، والخادم محمي من الاستخدام غير المصرح والطلبات المفرطة.
4. التثبيت النظيف والبناء والاختبارات تعمل من دون تجاوز تعارضات الاعتماديات.
5. التصدير اجتاز اختبارات عينات حقيقية ومراجعة بشرية قبل استخدامه في الإنتاج.

## نطاق العمل والمبادئ

- إصلاح المخرجات الوهمية والمضللة قبل إضافة مزايا جديدة.
- عدم إضافة حزم كثيرة لمجرد تكبير قائمة الاعتماديات؛ لكل حزمة مشكلة محددة وسبب وقياس قبول.
- الحفاظ على صور ومشروعات المستخدم عبر ترحيل واضح وعدم حذف بياناتهم بصمت.
- لا تُعرض عبارة «جاهز للطباعة/الليزر» إلا بعد تحقق آلي يناسب المعنى.
- لا تُعاد محاولة طلب ذكاء اصطناعي على كل أنواع الأخطاء؛ تُفرّق أخطاء المفتاح/الصلاحية عن الحصة المؤقتة ومشكلات الشبكة.
- يبقى وضع العرض التجريبي ممكنًا، لكن ببيانات موسومة بوضوح ولا تختلط بنتائج المستخدم الحقيقية.

- إنشاء ملف lockfile والالتزام به في Git، وتحديد نسخة Node المدعومة في `engines` وREADME.
- إصلاح تحذير `__dirname` في إعداد Vite باستخدام طريقة مناسبة لـ ESM، إن كان التحذير ما زال قائمًا في بيئة المشروع المستهدفة.
- تحديث اسم الحزمة وإصدارها، ومطابقة نسخة React المعلنة في README مع `package.json`.
- مراجعة ملف الرخصة: إضافة `LICENSE` مطابق فعلًا للحقوق أو إزالة ادعاء MIT.
- إضافة فحوص CI أولية: تثبيت نظيف، `npm run lint`، `npm run build`.

### معايير القبول

- `npm ci` أو أمر تثبيت نظيف مكافئ ينجح دون `--legacy-peer-deps`.
- ملف القفل متعقب، ونتيجة تثبيت بيئتين نظيفتين متطابقة.
- البناء وفحص الأنواع ينجحان، وكل وثائق الإصدارات والرخصة متسقة.

## المرحلة 1 — تصحيح الحقيقة وتجربة الذكاء الاصطناعي

**الأولوية:** P0 — إصلاح الثقة قبل أي إطلاق
**تقدير مبدئي:** 2–4 أيام عمل

### المهام

- إزالة استجابات التخرج الثابتة من مسارات التحليل وOCR والخطوط والألوان وتفكيك التصميم وتحليل البرومبت.
- عند غياب المفتاح أو فشل المزود: إرجاع حالة خطأ واضحة للمستخدم، مع `errorCode`/`providerUnavailable` مناسب، لا `success: true`.
- إن احتُفظ بوضع تجريبي: إنشاء بياناته في طبقة منفصلة، وإرفاق `source: "demo"` وإظهار شارة ثابتة «بيانات تجريبية» لكل نتيجة.
- إزالة الردود التي تدعي تنفيذ تغييرات فعلية في المساعد؛ ليقترح الإجراء أو ينفذه عبر عملية حقيقية موثقة.
- إزالة «اكتشاف حساب المتصفح» والبريد الثابت والحصص الوهمية. لا يُستخدم بريد نصي بديلًا عن OAuth أو تحقق ملكية الحساب.
- استبدال قسم الحسابات بواجهة إعداد مفتاح API، أو تنفيذ OAuth فقط إذا كانت هناك حاجة فعلية لتسجيل الهوية. لا تعرض أرقام حصة إلا من واجهة رسمية موثوقة.
- تدقيق أسماء النماذج وإعداداتها مقابل وثائق المزود وقت التنفيذ، وتسجيل اسم النموذج الفعلي الذي أنتج النتيجة.
- ضبط `generateWithFallback`: لا يعيد المحاولة في أخطاء المصادقة أو المدخلات غير الصالحة، ويضع مهلات/حدًا أقصى للمحاولات، ولا يخفي الخطأ الأصلي.
- تحديد سياسة واضحة لمزود التوليد الخارجي البديل. الخيار الافتراضي الموصى به: تعطيله. إن بقي، يلزم الإفصاح عن الإرسال لطرف ثالث، موافقة المستخدم، والتحقق من نجاح الطلب قبل إعلان النجاح.

### معايير القبول

- طلب صورة مختلفين لا ينتجان بيانات ثابتة متطابقة عند غياب المزود؛ بل يظهر فشل صريح أو وضع تجريبي معلّم بوضوح.
- المفتاح الخاطئ لا يعطي «اتصال ناجح» أو «رصيد مفعّل».
- لا يظهر رقم 1500 أو «مجاني» إلا إذا كان هناك مصدر موثوق وتوضيح نطاق الحصة وشروطها.
- اختبارات لكل حالة: مفتاح غائب، مفتاح غير صالح، انقطاع الشبكة، حصة منتهية، استجابة صحيحة، واستجابة غير قابلة للتحليل.

## المرحلة 2 — أمن الخادم والخصوصية

**الأولوية:** P0 قبل أي نشر عام
**تقدير مبدئي:** 2–5 أيام عمل، بحسب نموذج المصادقة والنشر

### المهام

- تحديد نمط التشغيل: أداة محلية لمستخدم واحد أم خدمة سحابية متعددة المستخدمين. لا يُعتمد النشر العام قبل حسم ذلك.
- إن كان عامًا: إضافة مصادقة وجلسات آمنة وتفويض لكل مشروع/مفتاح. إن كان محليًا: تقييد الوصول على الواجهة المقصودة وتوثيق ذلك.
- إضافة التحقق من المدخلات لأجسام الطلبات، الأنواع، أطوال النصوص، عدد الصور، أبعاد الصور، وأنواع MIME الحقيقية.
- تقليل `50mb` إلى حد مناسب لكل مسار. إضافة حدود معدل، وحدود للتوازي، ومهل زمنية، وحد أعلى لمعدل استهلاك المزود.
- إضافة رؤوس HTTP الأمنية وسياسة CORS/CSRF المناسبة لطريقة النشر، دون فتح كل المصادر افتراضيًا.
- منع قبول مفاتيح API من رؤوس أو أجسام عامة إلا عبر تدفق محدد وآمن. عدم طباعة المفاتيح أو إدراجها في رسائل الخطأ.
- إزالة حفظ المفاتيح من `localStorage`. اختيار تخزين خادمي آمن لمستخدم موثّق أو إدخال مؤقت غير محفوظ مع تنبيه واضح.
- مراجعة تصدير SVG/روابط الصور بحيث لا تُدمج بيانات غير موثوقة في SVG من دون تحقق صارم.
- وضع سياسة للاحتفاظ بالصور والبرومبتات، وحذف بيانات حساسة عند تسجيل الخروج أو حذف المشروع.

### معايير القبول

- الطلب غير الموثق أو الذي يتجاوز حد المعدل يُرفض دون استهلاك Gemini.
- الصور الكبيرة أو ذات الصيغة المخالفة تُرفض برسالة مفهومة قبل المعالجة.
- لا توجد مفاتيح API في التخزين الدائم للمتصفح أو في السجلات أو ملفات Git.
- اختبار إساءة الاستخدام لا يسبب استهلاكًا غير محدود أو تجمد الخدمة.

## المرحلة 3 — تنفيذ أداة الليزر بصورة صحيحة وآمنة

**الأولوية:** P0 لاستخدام تجاري؛ لا تفتح التصدير التشغيلي قبل الإنجاز
**تقدير مبدئي:** 5–10 أيام عمل للتنفيذ الأولي، إضافةً إلى اختبار ملفات وأجهزة

### المهام

- تحديد المدخلات والمخرجات المطلوبة: صور raster، وحدات القياس، DPI، نوع الخط، الطبقات، والقيود الخاصة بالماكينة.
- تنفيذ أو دمج خوارزمية raster-to-vector فعلية تنتج contours من الصورة المعالجة، لا أشكالًا ثابتة.
- تطبيق العتبة، التنعيم، التبسيط، عزل التفاصيل الصغيرة، وإغلاق المسارات على بيانات المتجهات الفعلية.
- حساب عدد المسارات والطول/المحيط والمسارات المفتوحة من الهندسة الناتجة. لا تُعرض تقديرات قطع زمنية إلا إذا وُضحت كـ «تقدير تقريبي» وربطت بسرعة الماكينة والمادة والإعدادات.
- إخراج SVG/DXF بوحدات ودقة واضحة، مع فحص إحداثيات خارج اللوحة، المسارات الذاتية التقاطع، الأشكال الفارغة، والقص خارج الحدود.
- إضافة معاينة منفصلة للنتيجة المتجهة، وإبقاء الأصل محفوظًا، وميزة تنزيل/تراجع آمنة.
- اختبار عينات معتمدة تشمل شعارًا، صورة رمادية، نصًا عربيًا، أشكالًا دقيقة، ومسارات مفتوحة/مغلقة. التحقق من فتح الملفات في أدوات مستهدفة يختارها المستخدم.

### معايير القبول

- يتغير SVG/DXF عند تغيير صورة الإدخال، ويمكن إثبات أن هندسته مأخوذة من نفس الصورة.
- تُطابق معاينة المسارات الملف المُصدّر، ويُظهر الفحص المسارات المفتوحة إن وجدت بدل إعلان إغلاقها تلقائيًا.
- تمر عينة مرجعية من الملفات إلى مستوردات برامج الماكينات المستهدفة دون أخطاء أو مقاسات خاطئة.
- تحذير بارز بأن التشغيل الفعلي يتطلب اختبار مادة/قدرة/سرعة على الجهاز قبل الإنتاج.

## المرحلة 4 — تجهيز الطباعة بمقاييس صحيحة

**الأولوية:** P1 قبل وصف أي ملف بأنه جاهز للطباعة
**تقدير مبدئي:** 3–7 أيام عمل، بخلاف ضبط الألوان مع مطبعة

### المهام

- فرض حدود عملية للأبعاد والـ DPI ومنع إنشاء Canvas بحجم غير محدود.
- قراءة أبعاد الصورة المصدر وحساب الدقة الفعلية عند حجم الطباعة، وإظهار تحذير/منع عند انخفاضها.
- جعل bleed تمديدًا حقيقيًا للصورة/التصميم أو توضيح أنه مساحة بيضاء، وليس مجرد قيمة مكتوبة.
- تطبيق safe area وعلامات القص في الملف النهائي حسب المواصفات المتفق عليها، لا في المعاينة فقط.
- استبدال مرشح CSS بتحويل لوني حقيقي وإدارة ملف ICC واتفاق مع المطبعة حول نوع الورق والملف المطلوب.
- تحديد صيغ التسليم: PDF/X أو TIFF أو PNG وفق احتياج المستخدم والمطبعة. عدم تسمية PNG بأنه CMYK إذا لم يكن كذلك.
- عرض بيانات الإخراج المؤكدة (الأبعاد بالبكسل، الدقة الفعلية، النمط اللوني، bleed، وملف اللون) مع تنبيه إذا كانت قيمة غير مضمونة.

### معايير القبول

- ملف الاختبار يحمل أبعادًا ودقة حقيقية متوافقة مع الإعدادات ولا يكتفي باسم ملف يتضمن `300DPI`.
- يطابق bleed وعلامات القص ما يظهر في المعاينة.
- يتم التحقق من الملف النهائي في برنامج تصميم/طباعة ومراجعته مع إعداد مطبعة فعلية.

## المرحلة 5 — التخزين والاستيراد والتصدير

**الأولوية:** P1 للاستقرار
**تقدير مبدئي:** 2–5 أيام عمل

### المهام

- إضافة رقم إصدار لمخطط البيانات وترحيلًا يتحقق من صحة JSON بدل قبول أي مصفوفة محليًا.
- نقل الصور والمرفقات الكبيرة من `localStorage` إلى IndexedDB، مع تنظيف وإدارة سعة ومساحة مستخدمة. يمكن البدء بواجهة IndexedDB أصلية أو حزمة صغيرة مثل `idb` عند الحاجة.
- إضافة نسخ احتياطي واستعادة موثوقة للمشاريع، والتحقق من محتوى الملف قبل الاستيراد.
- معالجة امتلاء مساحة التخزين برسالة ظاهرة بدل تسجيل الخطأ في console فقط.
- تحديد سياسات التراجع/الإعادة كي لا تنسخ كل المشروع الكبير في الذاكرة عند كل تعديل.

### معايير القبول

- مشروع كبير يحوي صورًا لا يفقد بياناته بصمت عند إعادة التحميل أو بلوغ حد التخزين.
- ملف استيراد تالف/غير متوافق يُرفض برسالة واضحة دون كسر التطبيق.
- توجد طريقة تصدير واستعادة جرى اختبارها على مشروع يتضمن صورًا وطبقات وبرومبتات.

## المرحلة 6 — الاختبارات وتجربة المستخدم والأداء

**الأولوية:** P1 قبل الإطلاق التجريبي
**تقدير مبدئي:** 3–6 أيام عمل، بالتوازي مع المراحل الأخرى

### المهام

- إضافة إطار اختبار متوافق مع Vite مثل `vitest`، واختبارات مكونات عند الحاجة. يمكن إضافة Testing Library إن كانت اختبارات تفاعل الواجهة مطلوبة.
- اختبار وحدات لدوال المعالجة والتحقق والتصدير، واختبارات API بمزود AI وهمي صريح لا يحاكي النجاح في بيئة الإنتاج.
- اختبار الاستخدام العربي/RTL والإنجليزي، الشاشات الصغيرة، لوحة المفاتيح، وحالات التحميل/الخطأ/الفراغ.
- تحميل الشاشات الثقيلة عند الطلب باستخدام dynamic import وتقسيم bundle، دون إخفاء التحذير بتغيير حد الحجم فقط.
- فحص استخدام لوحة المفاتيح وتباين الألوان ورسائل الخطأ وإمكانية الوصول الأساسية.

### معايير القبول

- جميع المسارات الحرجة لها اختبارات: عدم وجود مفتاح، فشل الشبكة، نجاح المزود، حفظ واستعادة، وتصدير/استيراد.
- لا تظهر نتائج نجاح زائفة عندما تفشل خدمة خارجية.
- لا توجد أخطاء Console حرجة أثناء جولة استخدام أساسية عربية وإنجليزية.
- حجم البداية الأولية ينخفض بوضوح عن القياس الحالي أو توثق أسباب بقائه مع ميزانية تحميل معتمدة.

## المرحلة 7 — التوثيق والنشر والتسليم النهائي

**الأولوية:** P1 للإطلاق
**تقدير مبدئي:** 1–3 أيام عمل بعد إغلاق المراحل السابقة

### المهام

- تحديث README بأوامر دقيقة للتثبيت المحلي والبناء والتشغيل والإنتاج، ومتطلبات Node ومزودي الخدمة.
- إنشاء `.env.example` بأسماء المتغيرات المطلوبة فقط، مع وصف آمن دون مفاتيح فعلية.
- توثيق ما هو محلي وما يُرسل إلى مزود AI أو خدمة طرف ثالث، وسياسة الخصوصية والتكلفة وشروط استخدام المستخدم لمفاتيحه.
- إضافة `/api/health` لا يكشف أسرارًا أو بيانات أكثر من اللازم، وربطه بفحص جاهزية مناسب.
- إعداد نشر تجريبي ثم فحص أمان واختبار استعادة/نسخة احتياطية، قبل توجيه نطاق الإنتاج.
- تحديد سجل تغييرات، نسخة إصدار، وخطة استرجاع للإصدار السابق.

### قائمة تحقق قبل الإطلاق

- [ ] لا توجد بيانات اعتماد أو بريد مستخدم ثابت في الكود.
- [ ] لا يوجد مسار يعيد نجاحًا تجريبيًا على أنه نجاح حقيقي.
- [ ] التثبيت والبناء والفحوص تنجح من CI دون تجاوز peer dependencies.
- [ ] قيود المصادقة ومعدل الطلبات وحجم الملفات مفعّلة.
- [ ] مفاتيح API غير موجودة في Git أو localStorage أو السجلات.
- [ ] التصدير الليزري والطباعة خضع لاختبار ملفات حقيقية ومراجعة متخصصة.
- [ ] سلوك إرسال البيانات إلى طرف ثالث واضح للمستخدم.
- [ ] النسخ الاحتياطي والاستعادة وحذف الحساب/المشروع مجربة.
- [ ] الوثائق والرخصة وإصدار المنتج متسقة.
- [ ] جرى اختبار يدوي عربي/إنجليزي على متصفح مستهدف.

| رؤوس الأمان | `helmet` | مناسبة لخادم Express؛ يجب ضبط CSP بما يلائم Vite والموارد الخارجية. |
| حد معدل | `express-rate-limit` أو حد على reverse proxy | اختر طبقة واحدة حسب البنية؛ في أكثر من نسخة خادم يلزم مخزن مركزي. |
| اختبار | `vitest`، وTesting Library عند اختبار الواجهة | أضف إطار الاختبار مع أول مجموعة اختبارات مفيدة. |
| معالجة/تحجيم الصور | `sharp` | عند وجود حاجة فعلية لتطبيع الصور على الخادم؛ راعِ حجم الحزمة والذاكرة. |
| Raster-to-vector | اختيار مكتبة tracing بعد تجربة مقارنة | لا يعتمد اسم مكتبة قبل اختبار دقتها ورخصتها وسلوكها مع النص العربي والشعارات. |
| تخزين المتصفح | IndexedDB أصلية أو `idb` صغيرة | انقل الصور الكبيرة إلى IndexedDB؛ لا تضف قاعدة بيانات كاملة بلا حاجة. |

**غير موصى به:** إضافة عشرات الحزم دفعة واحدة، استخدام مكتبة لمجرد أنها شائعة، أو إضافة خدمة خارجية جديدة قبل تحديد سياسة الخصوصية والتكلفة. يجب مراجعة الترخيص والصيانة والتوافق الأمني وإعادة اختبار تثبيت نظيف لكل حزمة جديدة.

## ترتيب التنفيذ المقترح

1. المرحلة 0: إصلاح الاعتماديات وإقامة خط بناء موثوق.
2. المرحلة 1: وقف النجاح الزائف وإزالة حسابات/حصص التمثيل.
3. المرحلة 2: تأمين الخادم والمفاتيح قبل إتاحته للعامة.
4. المرحلتان 3 و4: اختيار ترتيب الليزر والطباعة بحسب أول ميزة تجارية يحتاجها المستخدم؛ لا يُعلن أي منهما جاهزًا قبل معايير القبول.
5. المرحلتان 5 و6: بيانات موثوقة واختبارات وأداء بالتوازي مع تنفيذ الميزات.
6. المرحلة 7: نشر تجريبي، مراجعة، ثم إصدار إنتاجي.

**تقدير إجمالي تقريبي:** نحو 3–6 أسابيع لمطور خبير يعمل على المشروع بدوام كامل، إذا لم يتطلب الأمر OAuth متعدد المستخدمين أو تكاملات مدفوعة جديدة. قد تزيد المدة عند الحاجة إلى تحقق مع مزود API، توافق ملفات مع أجهزة محددة، أو اعتماد ألوان مع مطبعة. يبدأ الجدول الفعلي بعد تأكيد ميزات الإصدار الأول ونموذج النشر.
